--- A1. WHY does edge typing hurt?  RUNNING since 2026-08-16 19:06. See STATUS above. ---------
The n=7 family says WHICH component costs the graph its benefit but not why, and the paper currently
stops at "our encoder discards the signal". Naming the mechanism turns a diagnosis into a prescription,
which is what this venue's rubric rewards most.

WHAT IS ESTABLISHED. On the frozen fold at n=7: untyped +0.0904 > expression_only +0.0861 >
condition_gated +0.0818 > typed_static +0.0740. Edge typing is worth -0.0120 (7/7 seeds, survives both
corrections); the gate repairs only part of that and not significantly (+0.0077, bonf 0.131).

CANDIDATE MECHANISMS, none isolated:
  (i)   per-relation normalisation — already MEASURED to depress the mean gate tenfold (0.03 and 0.12
        against 0.73) in the arch search. Strongest suspect: the epoch-0 gate-collapse failure arriving
        through a second door.
  (ii)  the condition gate's initialisation.
  (iii) the decoder mixture gamma.
  (iv)  relation-specific parameter count — typed message passing has ~3x the parameters over the same
        edges, so this may be capacity/overfitting and not about types at all.

THE DISCRIMINATING EXPERIMENT. Add an arm with typed relations but weights SHARED across relation
types. It has the same parameter count as untyped and the same message-passing structure as typed.
  - behaves like untyped  -> the damage is parameter count (iv)
  - behaves like typed    -> the damage is the relation partition itself
Implement beside StaticTypedGraphEncoder in src/tcell_pipeline/baselines/graph_baselines.py; the
cheapest correct version shares one weight matrix across all relations rather than one per relation.
Run n=4 on the frozen fold in a FRESH root, paired against the existing expression_only lanes.
DECIDE IN ADVANCE, and write it into the prereg as a dated append BEFORE running: the comparison is
(shared-weight typed) - (typed_static). If it is positive and clears both corrections, parameter count
explains the damage; if indistinguishable, the relation partition does.

  - 5+ `run.py --encoding ...` quantum-ML jobs at ~99.5% CPU each.
  - Earlier, `launch.py --config configs/pfdv2.yaml --gpu 2` held 80,948 MiB of card 2's 81,920 - a
    CUDA context could not even be created there.
CONSEQUENCES for planning:
  1 These lanes are CPU-bound on row-by-row subgraph sampling (see UntypedGraphEncoder's docstring:
    "the batch is still sampled row-by-row on CPU, which is now the throughput floor"). Each lane uses
    about ONE core. GPU utilisation reads 100% and means very little.
  2 Per-epoch time therefore tracks whoever else is on the box: the same typed_static lane measured
    ~38 min/epoch when quiet, ~45 with three of ours running, ~80 once the Thyroid job appeared, and
    ~90 when six of ours competed. Quote ETAs as ranges and re-measure rather than extrapolating.
  3 ALWAYS map CUDA_VISIBLE_DEVICES to physical cards with torch's mem_get_info before scheduling.
    nvidia-smi index 3 is a T400, not an A100, and smi ordering is not CUDA ordering.
  4 Adding a worker is only worth it when the marginal CPU cost is small. Going 3->4 of our lanes costs
    one core out of 64 and gains a GPU; going 4->6 cost throughput outright.
  5 A FREE CARD DOES NOT STAY FREE. run_l4_card2.sh preflighted card 2 at 78 GiB free, started a lane,
    and 2h47m later a co-tenant reclaimed the card: the lane was SIGTERMed (exit 143) and the next four
    died instantly with CUDA OOM at "161 MiB free". A preflight is necessary and not sufficient. Any
    opportunistic worker on a shared card must (a) release its claim on failure so the main scheduler
    can retry - run_l4_card2.sh does - and (b) be treated as best-effort, never as the only path to a
    lane. Do not restart such a worker without re-checking the card; ours is at 68 GiB used again.
